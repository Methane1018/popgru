# 開發紀錄：踩過的坑

> 這裡只記**靜悄悄壞掉**的 bug —— 畫面看起來正常、資料卻一個字都沒寫進去的那種。
> 每一條在 `check.mjs` 都有對應的檢查，`./bump.sh` 會擋。

## 這個專案的 bug 有固定形狀

幾乎每個嚴重問題都長這樣：**前端照常運作、使用者看得到數字在動、但資料沒進資料庫。**
因為所有寫入都包在 `try/catch` 裡，失敗只是 `console.warn`，沒有人會發現。

所以現在：寫入失敗會 `console.error` 印出錯誤碼，連續三次會在畫面頂端顯示紅色橫幅。
**存不進去卻裝作沒事，比原本的 bug 更糟。**

---

## 1. `gName` 沒宣告 → 新用戶建不出格魯

`onSignedIn` 用了 `gName` 但從沒宣告。那行剛好在 `try` 裡，**ReferenceError 被 catch 吞掉，
整段 try 直接中止** —— 後面建立格魯的程式碼完全沒執行。

- 表面症狀：清空暱稱後顯示「無名氏」
- 真正後果：新朋友登入不會拿到格魯，不會出現在名單
- 教訓：`catch` 不可以吞掉程式錯誤。`ReferenceError` / `TypeError` 要 `console.error` 大聲叫

## 2. 待送匣讀寫格式不一致 → 補送永遠失效

`recoverOutbox` 讀新格式（`items` 物件），`outboxAdd` 卻還在寫舊格式（單一 `target`）。
兩邊對不起來，補送讀不到任何東西。

- 成因：多重字串替換的腳本中途 assert 失敗，**在寫檔之前中止**，把已經成功的替換一起丟掉
- 教訓：逐項寫檔並立即驗證，不要攢到最後才寫

## 3. `me.loaded` 從沒被設成 true → 計數欄位完全不寫

`flush()` 用 `if (me.loaded)` 決定要不要寫回連續天數等欄位，但沒有任何地方設過 `loaded = true`。
結果連續天數、凍結卡、雙倍魚、幫忙額度**整批停止寫入**。

- 成因：同 2，又一次
- 教訓：`check.mjs` 加了「flush 寫回的欄位必須等於快照讀入的欄位」

## 4. 誤把空的快取快照當成伺服器資料 ★ 最貴的一個

Firestore 的 `onSnapshot` **會先回一份本機快取的快照，再回伺服器那份**。
頁面剛載入時快取是空的，第一份是「一份不存在的空文件」。
程式把它當真 → 連續天數讀成 0 → `flush()` 又把 0 寫回伺服器 → 真資料被蓋掉。
**每次重整都發生一次。**

我為此連續猜錯四次，都在修下游症狀。真正定位是靠使用者貼出主控台。

- 教訓一：症狀模糊時，第一件事是**讓失敗變得可觀測**，不是讀程式碼推理
- 教訓二：守衛要精準。第一版擋掉「所有快取快照」，結果連正常資料都進不來（見 5）

## 5. 守衛過寬 → 寫入對象變成 `null`

修 4 的時候擋掉了所有快取快照，導致格魯快照永遠進不來，`state.viewing.uid` 一直是 `null`。
而 `flush()` 是 `if (n && target)`，**target 為 null 時整段跳過** ——
格魯和小圈子總數兩份資料完全沒寫，只有個人資料寫得出去。

- 正確做法：只擋「文件不存在 **且** 來自快取」。快取裡有資料的快照是安全的
- 安全網：在自己家時，寫入對象直接用 `state.me.uid`，不依賴 viewing 有沒有載好
- 舊資料修復：待送匣裡記成 `"null"` 的紀錄，補送時會算回自己身上

## 6. 登入時寫 `ownerName` → 暱稱每次重整被蓋掉

`onSignedIn` 寫 `ownerName: state.me.name` 到格魯，但那時個人資料快照還沒到，
`state.me.name` 還是 Google 名字 —— **暱稱根本還沒讀進來**。

- 修法：登入當下只寫頭像；`ownerName` 由 `syncOwnerName()` 在兩份資料都載入後才對齊

## 7. 刪函式刪過頭 → 「送人」整整壞了兩個版本

v0.8 重構商店時，我用「從 `function showHatPicker` 刪到下一個 `/* --- ` 註解」的方式移除舊函式，
結果把夾在中間的 `showGivePicker` 一起刪掉了（一次刪掉 136 行）。

按下「送人」只是靜靜地丟 `ReferenceError`，畫面毫無反應。兩個版本沒人發現，
因為我的測試從來沒有真的點過那顆按鈕。

- 教訓：**用行號範圍刪程式碼很危險**，要確認範圍內只有你想刪的東西
- 防線：`check.mjs` 現在會比對 `show*` / `panel*` / `draw*` 開頭的函式，
  被呼叫卻沒有定義就擋下來（已驗證這條檢查抓得到這個 bug）

## 8. 一個大約四成機率會紅的測試

`ok('魚 = 50', ...)` 偶爾失敗，重跑又好了，找不出原因。

原因是**寶物掉落是整包程式裡唯一用到亂數的地方**。壓 50 下大約有四成機率
隨機掉到一個帶「魚 +X%」的寶物，魚就會變成 51。

修法不是把斷言放寬，是**把亂數固定住**：測試開頭覆寫 `Math.random`，
預設回傳 1（永遠不掉），要測掉落時才調低。整包測試因此變成確定性的 ——
同一份程式碼永遠給同一個結果。

- 教訓：測試裡只要有一個不受控的隨機源，紅燈就會失去意義
- 附帶收穫：亂數固定之後，才寫得出「沒點技能就永遠掉不到傳說」這種端對端驗證

## 9. 點得下去、但什麼都不會發生的技能

技能樹的第四層（自動液壓機、魔法手）是純「權限」型的節點 ——
`grants:'autopress'` 只是一個字串，要有別的地方去問 `grants('autopress')` 才有意義。

如果忘記寫那段實作，節點照樣畫得出來、照樣點得下去、點數照樣扣掉，
**然後什麼都不會發生**。這跟「送人」按鈕壞掉兩個版本是同一類故障：
畫面上完全看不出來。

`check.mjs` 因此加了兩條互相對照的規則：

- 每個 `grants:'X'` 都必須有程式碼真的去問 `grants('X')`（否則是空的大招）
- 每個被問到的 `grants('X')` 都必須有技能給得出來（否則是永遠拿不到的權限）

兩條都實際驗證過抓得到：把 `grants('autopress')` 改掉，第一條立刻紅。

## 10. 新增一個鏡像欄位，把所有人的寫入卡死

v0.10.0 在 `MIRROR_FIELDS` 加了 `magicDay`。舊裝置的 localStorage 鏡像是 v0.9 寫的，
**沒有那個鍵**，於是第一次快照時：

    pickd[f] = useMirror ? mir[f] : srv[f];   // mir.magicDay === undefined

`undefined` 被塞進 `state.me`，接著 `flush()` 把它寫進批次 ——
**Firestore 收到 undefined 會拒絕整批寫入**，不是跳過那個欄位。

結果：連點擊都送不出去，連續九次寫入全部失敗。而畫面上一切正常，
只有主控台在噴。（幸好 v0.9 那次災難之後把寫入失敗改成 `console.error`，
不然這次又是無聲的。）

修的不是 `magicDay`，是那一行：抽成 `pickMirror()`，鏡像缺鍵就退回伺服器值。
這個坑跟欄位是什麼無關，**只要以後再加一個 MIRROR_FIELDS 欄位就會再踩一次**。

另外加了一道保險絲：`flush()` 寫出去之前把值為 `undefined` 的欄位刪掉並 `console.error`。
寧可少寫一個欄位，也不要因為一個欄位讓所有點擊都停擺。

三條 `check.mjs` 規則：鏡像欄位都要在 `blankMe()` 有預設值、都要出現在 `srv`、
`pickMirror` 要擋 undefined。已驗證第一條抓得到（把預設值刪掉就紅）。

- 教訓：**Firestore 的 undefined 是整批失敗，不是局部失敗**
- 教訓：新增一個「會被鏡像的欄位」是一個跨版本相容性問題，不是加一行

## 11. 學會的技能，過幾秒又變回「可以學」

`learnSkill()` 先改本機、再排進待送匣，最長 20 秒後才真的寫進 Firestore。
但快照處理是這樣寫的：

    skills: Array.isArray(d.skills) ? d.skills : [],

**直接照抄伺服器的值。** 中間任何一次快照回音（買個東西、改個名字都會觸發）
都會把還沒寫出去的那個技能抹掉 —— 於是節點又變回可以點。

`treasures` 一模一樣的寫法，只是掉寶比較少見所以沒人注意到。

這兩個欄位都是用 `arrayUnion` 寫出去的，也就是**只增不減**。
既然只增不減，快照要做的就是**取聯集**，不是替換：本機可能有還沒寫出去的，
伺服器可能有別的裝置加的，兩邊都要留。抽成 `mergeOwned()`。

（`ownedHats` 早就是這樣寫的，只是當時是為了相容舊資料，沒把它當成一條通則。）

`check.mjs` 因此加了一條會自己找欄位的規則：掃出所有
`queuePatch({ X: arrayUnion(...) })` 的 X，然後確認快照處理裡的 X 是走 `mergeOwned()`。
**以後再加任何一個 arrayUnion 欄位，忘了合併就會被擋下來。** 已驗證抓得到。

- 教訓：`increment` 的欄位要加上本機待送量，`arrayUnion` 的欄位要取聯集。
  兩者都不能照抄伺服器 —— 快照永遠比本機慢一拍

## 12. 同一個 bug 修了兩次才修對

v0.10.3 把快照處理改成 `mergeOwned()` 取聯集，但使用者回報**技能還是會變回可以學**。

第一次只修了「讀」，沒修「寫」。`learnSkill()` 是這樣寫的：

    queuePatch({ skills: fb.F.arrayUnion(id) });   // 排一筆，等 flush 送出去

而 **`pendPatch` 不在待送匣裡**。待送匣只保得住點擊數（n/fish/gold）。
所以只要那一筆遇到寫入失敗（例如 v0.10.1 那段所有寫入被拒的期間）
又剛好關掉頁面，它就永遠消失 —— 伺服器上沒有那個技能，重整之後就又能學一次。

真正的修法是不要倚賴那一筆 patch 活到成功為止：

    if (me.skills?.length)    p.skills    = F.arrayUnion(...me.skills);
    if (me.treasures?.length) p.treasures = F.arrayUnion(...me.treasures);

**每次 flush 都把完整清單整份 union 回去。** arrayUnion 是冪等的，
成本只有幾個字串，而且任何一次遺失都會在下一次寫入時自己補回來。

- 教訓：**「排一筆補償寫入」跟「每次都對帳」是兩種可靠度**。
  前者只要斷一次就永久遺失，後者會自癒
- 教訓：修 bug 時要問「讀和寫兩邊都修了嗎」。我當時只看了讀的那一半

## 13. 進度條取整之後永遠是 0

金魚門檻 350，壓一下是 0.28%，`Math.round()` 之後是 0 —— 進度條看起來完全沒動。
改成 `toFixed(2)`。小事，但那正是「看起來壞掉」的樣子。

## 14. 「重壓學會了，熟練卻沒有」—— 使用者給的線索破了案

同一個 bug 修了三次。前兩次都是猜，第三次是因為使用者多說了一句：

> 我的「熟練」技能依舊還是未點的狀態，明明我的「重壓」技能是點好的

**那個狀態不可能靠正常操作產生** —— 學重壓一定要先有熟練，有前置檢查。
所以問題一定出在「兩筆寫入之間」，而不是「讀回來的時候」。

    const queuePatch = p => { pendPatch = { ...(pendPatch||{}), ...p }; };

物件展開合併，**同一個 key 的第二筆會把第一筆整個蓋掉**：

    學會熟練 → { skills: arrayUnion('press1') }
    還沒送出去就學了重壓 → { skills: arrayUnion('press2') }   ← 蓋掉上一筆

伺服器只收到 press2。同樣的機制也讓「連買兩個寶物只扣到後面那一筆的錢」。

根本問題是**把已經做好的 FieldValue 堆在一個用覆蓋方式合併的容器裡**。
FieldValue 是不透明的，合併不了。改成只記「意圖」：

    queueInc('goldfish', -5)     // 相加
    queueUnion('skills', 'x')    // 取聯集
    queueSet('spBought', 3)      // 絕對值，新的贏

FieldValue 等到 flush 要寫的時候才組出來，合併規則才會是對的。

另外加了 `repairSkills()`：擁有第 N 層就代表前面每一層都付過錢，缺的直接補回去。
既有的壞資料開一次頁面就會自己修好。

- 教訓：**不透明的物件不能放進會合併的容器**。要放就放能合併的原始意圖
- 教訓：症狀的「不對稱」是最好的線索。如果兩個技能都不見，我會繼續猜讀取；
  正因為只有前面那個不見，才指得出是寫入時互相覆蓋
- `check.mjs` 加 6 條，其中兩條驗證過抓得到

## 15. 重新整理就白拿 3000 下

朋友回報的。小圈子總數被灌到十萬。

三段各自都合理的程式碼，湊在一起變成無限刷：

1. `applyGuest()` —— 開頁先當訪客
2. `prefillFromMirror()` —— 把會員的累計填進 `state.me`，**免得畫面閃 0**
3. `saveGuest()` —— 訪客模式下每次壓都存檔

問題是 **Firebase 認證是非同步的**。第 2 步發生時 `mode` 還是 `'guest'`，
所以那個空檔裡點一下，`saveGuest()` 就把「會員的五萬下」寫成訪客進度。
認證一回來，`claimGuestProgress()` 把它當新玩家的成果補算：
`min(50000, 3000) = 3000`，個人、自己的格魯、**小圈子總數**各加 3000。

每次重整都來一遍。

修法兩層：

- `mirroredMe` 旗標：畫面上的數字一旦是從會員備份墊上去的，`saveGuest()` 就拒絕寫入。
  登出回到訪客身分才清掉
- **一個帳號只補算一次**（`claimedGuestAt` 蓋章）。「把訪客時期的成果帶進來」
  本來就是一次性的事，少了這道閘，任何一個讓訪客存檔重新出現的 bug 都會變成無限刷

- 教訓：**「為了畫面好看而先填假資料」會被下游當成真資料**。
  墊畫面的值一定要標記出來，不能跟真的混在一起
- 教訓：非同步的身分狀態下，「現在是誰」在整段載入期間都不能當成已知
- 6 條 `check.mjs` 規則；回歸測試驗證過會抓到（訪客存檔裡出現 `lifetime: 50001`）

## 16. 買了東西，畫面把錢退回去

用金魚買寶物，金魚扣掉了，點一下又變回原來的數目 —— 等於免費。

快照處理很早就寫對了一半：

    goldfish: (d.goldfish||0) + pendGold + inflight.gold,

「伺服器的數字 ＋ 還沒送出的量」。但 `pendGold` 只涵蓋**賺到的**金魚，
**花掉的**金魚排在 `pendInc` 裡，這條算式沒把它加進來。
於是在扣款真正寫到伺服器之前，任何一次快照回音都把錢退回來。

修的是那條算式（`pendIncOf()`，同時涵蓋排隊中和送出中的扣款），
不是某一個購買函式 —— 三種貨幣、所有購買路徑都是同一個問題。

順便把 `buySkin()` 和 `buyForSelf()` 從「自己 setDoc 一份」改成走同一個佇列。
它們自己寫的話，扣款就不在 `pendInc` 裡，一樣會退錢。
現在整個檔案只剩登入那一次直接寫 `users`，而且 `check.mjs` 會數。

- 教訓：**「伺服器值 ＋ 未送出的量」這條算式，加項要涵蓋每一個會動那個欄位的路徑。**
  漏掉一條，那條路徑上的操作就會被快照抹掉
- 教訓：同一個欄位有兩套寫入機制（佇列 vs 各自 setDoc），遲早會不同步。統一走一條

## 17. 收集完之後，遊戲自己壞掉

金魚門檻本來是：

    Math.max(1, Math.round(TUNING.goldfishOdds * (1 - buffOf('gold'))))

而 gold 增益全部收齊 —— 🔮 水晶球 .20 ＋ 🌠 極光 .30 ＋ 🕛 準時 .10
＋ 📜 追本溯源 .15 ＋ 🪨 重壓 .25 —— **剛好是 1.00**。

`350 × 0 = 0`，夾成 1，**每點一下掉一條金魚**。

`(1 - X)` 這個形式只要 X 逼近 1 就會退化，而收集遊戲的增益本來就是
「越收越多」—— 這兩件事湊在一起是遲早的事，不是巧合。

改成除法：`門檻 ÷ (1 + X)`。X 的意思變成「快幾倍」，永遠除不到 0，
而且跟畫面上寫的「更容易掉 +25%」對得起來（1.25 倍）。全收齊是 2 倍。

折扣仍然是 `原價 × (1 - X)`（那個語意本來就對），但加了天花板 `maxDiscount`，
免得以後折扣寶物越加越多變成免費。

真正的收穫是那個測試：**把所有寶物和技能都給一個假玩家，然後檢查每條算式還正常。**

    S.state.me.treasures = ALL.map(t => t.id);
    S.state.me.skills    = ALLSK.map(s => s.id);

金魚門檻 > 1、每個道具還要錢、幫忙額度有限、掉寶機率 < 1。
以後再加任何寶物或技能，只要讓某條算式退化就會在這裡紅。

- 教訓：**增益要用乘除，不要用「減掉百分比」**。前者不會退化，後者有個懸崖
- 教訓：平衡性的 bug 也可以寫成測試 —— 條件是「模擬極端的玩家」而不是「模擬極端的輸入」

## 18. 一個事件穿兩件衣服（潮邊的提議）

> 我覺得壓扁格魯可以和金魚分開 …… 讓壓扁格魯變成隨機事件，
> 然後金魚每若干下就會掉，讓壓扁格魯稀有一點，獎勵也多一點

原本「格魯攤在地上三秒」和「掉一條金魚」是**同一個事件**。
拆開之後才看得出來，綁在一起讓兩邊都做不好：

- **金魚明明是可預期的，卻裝成隨機。** 它是固定計數（`goldTick`），
  畫面上還有進度條寫著「還差幾下」，卻用一個看起來像中獎的動畫呈現
- **整個遊戲最好笑的畫面被鎖死在固定節奏上。** 攤地動畫每 350 下必定出現一次，
  可預測的驚喜就不是驚喜

拆開之後各自做該做的事：

| | 機制 | 感覺 |
|---|---|---|
| 🥇 金魚 | 固定每 350 下，有進度條 | 穩定收入，努力就拿得到 |
| 😵 攤了 | 隨機 1/500 | 真的會「喔！」的那一下 |

而且攤了現在配得上它的稀有度：一次 150 條魚，那一下的掉寶機率乘 8 倍。

- 教訓：**一個事件同時承擔兩種意義時，兩種意義都會被拖累。**
  可預期的東西要長得可預期，隨機的東西才有資格演一場
- 攤的機率也用除法（`flatOdds / (1 + 增益)`），不會重蹈第 17 條的覆轍

## 19. 進度條「沒跟上」—— 其實是兩個 bug

潮邊回報進度條怪怪的，和運直接猜中了分母：

> 會不會是 (317208 - X) / (500000 - X)，X 是上一個門檻

正是。而查下去發現是**兩個獨立的問題疊在一起**：

**一、進度條和它旁邊的字在講不同的事。**
進度條算的是「這一段走了多少」（250k → 500k 之間走了 27%），
旁邊的字寫的卻是「距離『五十萬』還有 182,792 下」。
於是大家自然把進度條讀成 317208 / 500000 = 63%，看到 27% 就覺得壞了。

兩個都「對」，但擺在一起就是錯的。改成對下一個門檻的絕對比例，
並且把分子分母直接寫出來（`317,208 / 500,000`），不留想像空間。

**二、小圈子總數根本不含本機還沒送出的點擊。**

    const shown = st.global.squashes;      // 上一次寫入時的快照

個人累計老早就是「伺服器的數字 ＋ 待送量」了（第 6 條的教訓），
小圈子總數卻一直漏掉 —— 所以你連壓 20 秒，大數字和進度條都完全不動，
然後突然跳一大格。這才是字面上的「沒跟上」。

順手也把帽子／外觀的解鎖判定改用同一個數字，
不然會出現「進度條說到了，東西卻還鎖著」。

- 教訓：**同一個資料有兩種呈現時，它們必須是同一個算式的兩種寫法。**
  各自都合理不代表擺在一起合理
- 教訓：第 6 條那個「快照加回待送量」的修法，當時只修了個人欄位。
  同一類的地方要一次找乾淨
- 值得記的是：使用者只說「有點沒跟上」，是他們自己算出分母才定位到的。
  把實際數字（317208、500000）講出來的回報，比任何描述都有用

## 資料庫用量

每次 flush 寫三份文件（`users` / `grus` / `meta/global`），三份都掛 `onSnapshot` ——
**寫下去就回推一次快照，那就是一次讀取**。所以「多久寫一次」直接決定每小時燒多少額度。

一度設成停手 1.5 秒就寫，單人每小時就燒掉約 7,200 次讀取。現在是 6 秒 + 20 秒保底，約 1,800。

放慢寫入不會掉資料：真正保命的是 `popgru.outbox`（待送匣）和 `popgru.mirror`（本機鏡像），
都在 localStorage，關頁面／當掉／離線都還在。
