## 一句話

**v1.0 = 格魯不再只是兩張照片。**

v0.8～v0.11 加的都是「圍繞在格魯旁邊的系統」（商店、圖鑑、技能樹）。
v1.0 要回到中間那隻企鵝身上：它會有更多樣子、會被更多東西攻擊、
而且它背後有一段可以走進去的故事。

## A. 美術翻新

兩個提案，以及我的看法：

**提案 1：輪流播放各種攻擊動畫**
主格魯身上輪流出現錘子、球棒、液壓機的攻擊。

**提案 2：主格魯周圍放分身，各自被不同的手段攻擊**
右上、左下之類的位置放小格魯，每個對應一種放置手段。

### 建議：走提案 2，但加一條限制

理由：**提案 2 讓「進度」變成看得見的東西。** 解鎖第五種手段時，
畫面比第一種明顯更熱鬧；提案 1 不管解鎖幾種，同一時間都只看得到一個。
放置類遊戲最爽的就是「看著自己的工廠越長越大」。

限制：**主格魯必須維持視覺主角，而且不被自動化碰到。**
中間那隻永遠只回應你的手指 —— 那是核心笑點的所在地。
自動化發生在周圍的分身身上。

拼貼風格剛好支援這件事：分身可以是小尺寸照片、工具可以是別的風格，
不需要跟主體同一個畫風。

**待決定**：分身要幾隻？固定位置還是隨解鎖數量重排？

## B. 放置成長手段

錘子、球棒（bonk）、液壓機。

### 跟現有的「自動液壓機」怎麼銜接

目前 `press4 自動液壓機` 是壓製軸的終點（5 點），效果是「開著頁面就自動壓」。
新的三種手段如果各自獨立，那它就從「一個技能」變成「一整條產線的第一格」。

兩種接法：
1. **保留 press4 當作「解鎖放置系統」的鑰匙**，錘子／球棒／液壓機是之後的節點
2. **把 press4 改名成錘子**，另外兩個接在後面

傾向 1：`自動液壓機` 這個名字已經寫在更新紀錄裡，而且「解鎖一整個系統」
比「解鎖一個工具」更配得上一條軸的終點。

### 兩個要先想清楚的問題

**問題一：放置產出算不算進小圈子總數？**

**已定案（2026-09-08）：算進去。**

理由：那個數字的意義是「我們總共壓了幾下」，為了節奏而讓它說謊更糟。

連帶要做的事：**里程碑要往上加。** 現在最高是一百萬，
放置一開就會很快破掉，屆時進度條會直接消失（`MILESTONES.find(m => m.at > shown)`
找不到就藏起來）。加放置手段的同一版就要補上後續的里程碑。

**問題二：放置產出算不算連續天數？**

**不算。** 這條 v0.10 就定案了，不要動 —— 連勝是唯一防得住的指標。

## C. 技能樹：從 forest 變成真正的 tree

現在是三條各自獨立的鏈（壓製／社交／探寶），共用一池技能點。
你說得對，那是 forest 不是 tree。

### 單一起點的樹會多出什麼

老實說，**光是「單一起點」本身不會增加深度** ——
三條鏈共用點數的時候，選擇壓力就已經存在了。

真正會增加深度的是**跨支節點**：需要兩條支線都有進度才能點的節點。
那會產生「身分」：走壓製＋探寶的人跟走社交＋探寶的人，
玩起來是兩種不同的遊戲，而不是同一個遊戲的兩種數值配置。

### 建議結構

```
                    ┌── 壓製 ──┬── 放置手段（錘子／球棒／液壓機）
    起點 ──────────┼── 社交 ──┤
                    └── 探寶 ──┴── 跨支節點（要兩邊都有進度）
```

要保留的性質：
- **免費技能點永遠點不滿整棵樹**（`check.mjs` 有一條在守這個）
- **不做洗點**
- 樹上永遠有你看得到、但現在點不起的節點

## D. 兔子洞：劇情彩蛋

點進去會觸發一段劇情，可能是解謎、可能是長篇挑戰。
**隨時可以回到原本的遊戲**，不會被卡住。

### 你自己指出的矛盾

> 完成後可以用這個劇情的名字來命名一個神話等級寶物
> （雖然這樣又會跟「彩蛋寶物自成一種稀有度」相悖）

確實相悖。彩蛋不標稀有度的理由是「稀有度會洩漏它有多難，而彩蛋的重點是自己撞到」。

### 建議：兔子洞不是彩蛋，是新的一類

新增第五種來源 **`story` 劇情**，跟 `drop`／`achieve`／`egg`／`shop` 並列，
有自己的顏色。

這樣兩條規則都不用破：

| | 彩蛋 | 劇情 |
|---|---|---|
| 本質 | 你自己撞到的小秘密 | 你走完的一段路 |
| 藏不藏 | 藏（提示要隱晦） | **不藏**，兔子洞看得見，只是進不去 |
| 標稀有度 | 不標（會洩漏難度） | **標**，因為沒有東西要防洩漏 |

「看得到但還進不去」正好就是這個專案已經定案的深度原則
（技能樹的大招也是這樣）。所以兔子洞可以大方地擺在畫面上，
而它給的寶物可以正大光明地掛著 🟡 神話。

**待決定**：兔子洞的入口放哪裡？進入條件是什麼？

## 我建議先做的一件事（地基）

v0.11.0 到 v0.11.4 連續五個 bug 全部是同一家族：
**本機狀態與伺服器狀態沒有單一真相**。而且其中三個是「測試碰不到」——
出問題的程式碼都在 `flush()` 和快照處理裡面，兩者都需要連線才跑得動。

v1.0 會加入放置產出、劇情進度、更多技能狀態，
這些全部都要存、都要同步。**在同一塊沙地上蓋更高的樓，只會摔得更重。**

建議先把 `flush()` 和快照處理拆成「決定要寫什麼」（純函式、測得到）
跟「送出去」（薄薄一層網路）。做完之後這一整類 bug 會被測試蓋住，
而不是等朋友回報。

估計比一個功能小，但會讓後面每一個功能都便宜。

# 地基重構（v0.12）

> 開工日：2026-09-08。這一段是為了讓 v1.0 的新狀態有地方安全地放。

## 要解決什麼

v0.11.0～v0.11.4 連續五個 bug，全部同一家族：

| 版本 | 症狀 | 根因 |
|---|---|---|
| 0.10.5 | 學會的技能又變回可以學 | `pendPatch` 用覆蓋合併，同 key 互相蓋掉 |
| 0.10.9 | 買東西之後畫面把錢退回去 | 快照重算漏掉「花掉的」 |
| 0.11.2 | 進度條沒跟上 | 小圈子總數不含待送量 |
| 0.11.3 | 送的東西收不到 | 收信箱只寫伺服器、不動本機 |
| 0.11.4 | 幫過三個人達不成 | `set()` 不把點號當路徑 ＋ 快照照抄 |

**共同點：本機狀態與伺服器狀態沒有單一真相，而且錯的地方測試碰不到。**
出問題的程式碼都在 `flush()` 和快照處理裡面，兩者都要連線才跑得動。

## 怎麼做

把兩段各自拆成兩層：

```
現在                          之後
─────────────────────────    ─────────────────────────────────
flush()                       planFlush(狀態)  →  純函式，回傳「要寫什麼」
  取待送量                                        測得到
  組 FieldValue               ─────────────────────────────────
  組批次                      flush()          →  薄薄一層
  commit                        materialize + commit + 善後
  善後
─────────────────────────    ─────────────────────────────────
onSnapshot 回呼               planSnapshot(舊狀態, 伺服器資料)
  一大坨合併規則                                → 純函式，回傳「me 要變成什麼」
  Object.assign                                   測得到
                              ─────────────────────────────────
                              回呼               →  Object.assign + emit
```

關鍵原則：**純函式回傳的是「意圖」不是 FieldValue**
（`{__inc: 5}` 而不是 `increment(5)`）。這條 v0.10.5 已經學過一次 ——
FieldValue 是不透明物件，放進任何會合併的容器都會出事。

## 驗收標準

- `planFlush` 和 `planSnapshot` 完全不 import Firebase
- 上面那五個 bug 每一個都有一條「純邏輯測試」抓得到
- `check.mjs` 有規則擋住「把合併邏輯寫回網路層」
